# PreCTG 아키텍처 및 구현 계획

이 문서는 PreCTG MVP의 확정 기술 스택, 모듈 책임, 처리 흐름, 단계별 구현 순서와 RiskGate 활용 경계를 정의합니다.

## 1. 설계 원칙

- 실제 데이터가 들어오면 입력 어댑터와 구성만 바꾸어 동일한 처리 흐름을 검증할 수 있게 한다.
- 규칙 기반 판단과 ML 예측을 분리해 각각의 근거와 실패 원인을 확인할 수 있게 한다.
- 모든 특성에 가용 시점을 부여하고 사후 정보와 목표 라벨의 입력 사용을 자동 차단한다.
- CPU·폐쇄망에서 재현 가능한 단순한 구성으로 제한한다.
- 합성 데이터 성능과 임상 성능을 코드, 화면, 문서에서 명확히 구분한다.
- UI보다 검증 가능한 도메인 함수와 CLI를 먼저 완성한다.

## 2. 확정 기술 스택

| 영역 | 기술 | 선택 이유 |
|---|---|---|
| 언어 | Python 3.11 | 데이터·ML 생태계와 로컬 개발 재현성 |
| 표 형식 처리 | pandas, NumPy | AIHub JSON/CSV 정규화와 합성 데이터 생성 |
| 스키마 검증 | Pydantic 2 | 입력 타입·코드·범위와 오류 메시지 계약 |
| 전처리·평가 | scikit-learn | Pipeline, 그룹 분할, 지표와 보정 도구 |
| 핵심 ML | LightGBM | CPU에서 빠른 표 형식 분류와 RiskGate 경험 재사용 |
| 모델 직렬화 | joblib | 로컬 모델 저장·로드 |
| 시각화 | matplotlib, seaborn | 분포·단계별 변화·특성 기여 요약 |
| 데모 UI | Streamlit | 짧은 개발 시간으로 입력·결과 흐름 시연 |
| UI 글꼴 | Pretendard | 한국어 가독성과 일관된 데모 화면 |
| 테스트 | pytest | 규칙, 스키마, 누수와 통합 흐름 자동 검증 |
| 품질 도구 | Ruff | 포맷과 정적 검사 단일화 |
| 의존성 관리 | `requirements.txt`와 고정 버전 | 폐쇄망 반입과 단순한 재설치 우선 |

딥러닝 프레임워크, 클라우드 데이터베이스, 외부 추론 API와 원격 텔레메트리는 현재 MVP에 도입하지 않는다. Python 3.11은 로컬 기준이며 본선 안심존 버전이 다르면 호환 가능한 범위에서 구성만 조정한다.

Pretendard는 외부 CDN에만 의존하지 않고 폐쇄망에서도 표시할 수 있게 로컬 자산으로 제공한다. 로드에 실패하면 운영체제의 한국어 산세리프 글꼴로 대체하며, 핵심 기능과 텍스트 가독성이 영향을 받지 않아야 한다.

## 3. 논리 아키텍처

```text
AIHub 호환 JSON/CSV 또는 데모 입력
                  |
          스키마 검증·정규화
                  |
       +----------+-----------+
       |                      |
분만 전 EMR 특성          초기 CTG 특성
       |                      |
0단계 규칙 위험도        1단계 CA 규칙 판정
       +----------+-----------+
                  |
          누수 검사·특성 조립
                  |
        2단계 LightGBM 추론
                  |
          통합 경보·근거 생성
                  |
          JSON / CLI / Streamlit
```

0단계와 1단계는 ML 모델이 없어도 실행되어야 한다. 2단계 모델 파일이 없거나 입력 품질이 기준에 미달하면 이를 명시적으로 보고하고 규칙 결과를 ML 결과처럼 위장하지 않는다.

## 5. 단계별 구현 계획

### 단계 0: 계약과 근거 고정

산출물:

- AIHub 원본 필드와 내부 표준 필드 매핑
- 필드별 타입, 코드, 단위, 결측 표현과 가용 시점
- 누수 금지 목록
- 임상 규칙과 합성 분포 근거 레지스트리
- 대표 정상·경계·고위험·결측 사례의 기대 결과

완료 조건:

- 모든 모델 후보 특성에 시간 분류가 존재한다.
- 확인되지 않은 임상 임계값이 `approved` 규칙으로 남아 있지 않다.

### 단계 1: 입력 스키마와 정규화

산출물:

- Pydantic 입력 모델
- AIHub 호환 JSON/CSV 어댑터
- `9999`와 코드형 문자열의 내부 변환
- 유효성 오류 메시지와 소형 fixture

완료 조건:

- 정상 입력은 동일한 내부 레코드로 변환된다.
- 누락, 잘못된 코드와 범위 밖 값은 예상한 오류를 반환한다.

### 단계 2: 합성 데이터 생성기

산출물:

- `distribution`과 `coverage` 생성 프로필
- 시나리오·조건부 분포·합성 라벨 생성
- 고정 시드, 버전·근거 추적 정보
- 품질 검사 보고서

완료 조건:

- 500건 소규모 생성에서 스키마·논리·재현성 검사가 통과한다.
- 이후 5,000~10,000건과 50,000건 이상으로 같은 계약을 확장할 수 있다.

### 단계 3: 0단계 EMR 위험도

산출물:

- 승인된 규칙의 점수 계산
- `risk_score`, `risk_group`, `risk_reasons`
- 경계값과 복합 위험 사례 테스트

완료 조건:

- 결과의 모든 점수는 적용 규칙과 입력값으로 역추적할 수 있다.
- 분만 이후 정보 없이 실행된다.

### 단계 4: 1단계 초기 CTG 규칙

산출물:

- 승인된 분류 기준에 따른 CA 후보 판정
- 충돌 시 우선순위와 판정 근거
- 규칙 경계·충돌 사례 테스트

완료 조건:

- 동일 입력은 결정적으로 같은 범주와 근거를 반환한다.
- 공식 `CA` 라벨 없이 계산되며, 라벨은 비교 검증에만 사용한다.

### 단계 5: 2단계 LightGBM

산출물:

- 전처리와 모델을 묶은 학습 Pipeline
- 그룹 단위 데이터 분할
- 특성 시점·누수 자동 검사
- 모델, 특성 목록, 구성과 버전 저장
- Model A와 선택적 Model B 비교

Model A는 EMR과 원시 초기 CTG 특징만 사용한다. Model B는 같은 특성에 규칙 기반 CA 결과를 추가해 정보 누적 흐름을 시연한다. 합성 데이터 결과는 기능 점검과 회귀 테스트 용도로만 사용한다.

완료 조건:

- 같은 시드로 학습 산출물을 재현한다.
- 목표·사후·생성 메타데이터 열을 넣으면 학습이 실패한다.
- 저장한 모델을 별도 프로세스에서 불러와 같은 입력을 추론한다.

### 단계 6: 통합 Risk Engine과 설명

산출물:

- 단일 `predict` 진입점
- 단계별 결과, 통합 경보, 입력 완전성과 근거
- 모델 부재·저품질 입력·지원하지 않는 코드 처리
- JSON 직렬화 계약

완료 조건:

- 대표 사례 전체가 입력부터 결과까지 실행된다.
- 규칙 결과, ML 결과와 입력 품질 상태가 서로 다른 필드로 표현된다.

### 단계 7: CLI와 Streamlit 데모

산출물:

- 생성, 학습, 단일 예측과 배치 예측 CLI
- 사례 선택·직접 입력·결과 표시 Streamlit 화면
- 단계별 위험 변화, 주요 근거와 경고 시각화

완료 조건:

- 새 로컬 환경에서 문서화된 명령으로 재현된다.
- 화면과 JSON의 값과 용어가 일치한다.
- 모든 화면에 합성 데이터·비임상용 경고가 보인다.

### 단계 8: 시연 증거와 본선 전환 준비

산출물:

- 50,000건 생성·배치 처리 보고서
- 대표 사례 화면 캡처
- 기능 테스트와 누수 검사 결과
- 실제 데이터 반입 시 교체 지점 목록

완료 조건:

- 제안서에 사용할 모든 숫자와 화면의 생성 절차를 재현할 수 있다.
- 실제 성능으로 오해할 표현이 없다.

## 6. RiskGate 활용 방안

RiskGate는 코드 전체를 복제하는 템플릿이 아니라 검증된 구현 패턴의 참고 자료로 사용한다.

### 6.1 재사용할 패턴

| RiskGate 패턴 | PreCTG 적용 |
|---|---|
| 단계별 정보 누적 모델 | EMR → 초기 CTG → 규칙 결과 추가 비교 |
| feature engineering 모듈 분리 | 원본 매핑, 파생 특성, 모델 특성 책임 분리 |
| `risk_score`, `risk_group`, `high_risk_reason` | 0단계 위험 점수와 설명 계약 |
| 명시적 leakage column 차단 | 필드별 가용 시점과 학습 전 실패 검사 |
| 환자 단위 분할 | 산모·태아 식별자 기반 그룹 분할 |
| 입력 JSON 정규화 | AIHub 호환 입력을 내부 표준 스키마로 변환 |
| 결측 비율과 상황 설명 | `data_completeness`와 누락 필드 설명 |
| 모델 저장·로드와 CLI | 재현 가능한 로컬 학습·추론 흐름 |
| Situation Manager | 단계별 근거를 사람용 문장으로 변환하는 설명 계층 |

### 6.2 재사용하지 않을 도메인 코드

- 수술 시간 예측 목표와 회귀 모델
- 수술 시작 후 30분 활력징후·약물·수혈 특성
- ASA, 수술명, 수술실 운영 위험 규칙
- 수술 지연 fallback 계산
- 수술실 상황·권고 문구와 임계값
- RiskGate 데이터 로더의 INSPIRE 전용 결합 로직

이 코드는 PreCTG의 태아·산모 도메인으로 이름만 바꾸어 복사하지 않는다.

### 6.3 재사용 절차

1. RiskGate에서 재사용 후보의 책임과 테스트 가능성을 확인한다.
2. 의료 도메인에 독립적인 작은 패턴만 PreCTG 인터페이스로 다시 구현한다.
3. 기존 코드 복사가 필요한 경우 출처 파일과 변경 이유를 기록한다.
4. PreCTG의 스키마·누수·오류 테스트를 통과한 뒤 유지한다.
5. RiskGate와 PreCTG 사이에 런타임 파일 경로나 모델 산출물 의존성을 만들지 않는다.

## 7. 검증 전략

- 단위 테스트: 코드 변환, 결측 처리, 임상 규칙, 경계값, 누수 차단
- 속성 테스트: 생성 값의 범위, 불변조건, 동일 시드 재현성
- 통합 테스트: JSON/CSV → 단계별 결과 → 직렬화
- 모델 테스트: 그룹 분할, 특성 계약, 저장·로드 동일성
- UI 점검: 대표 사례의 값·근거·경고 일치, Pretendard 로컬 로드, 대체 글꼴 동작과 한국어 가독성
- 처리량 점검: 50,000건 생성과 배치 추론 시간·오류 건수

합성 데이터 지표는 모델 구현 오류를 찾는 회귀 기준으로만 사용한다. 실제 데이터 확보 전에는 임상 성능 합격 기준을 정의하지 않는다.

## 8. 생성물과 저장소 정책

- 자동 테스트에 필요한 소형 합성 fixture만 저장소에서 관리한다.
- 대규모 합성 데이터, 학습 모델, 생성 그래프, 로그와 실행 결과는 코드·구성으로 재생성하고 Git에 포함하지 않는다.
- 실제 의료데이터와 환자 단위 정보는 저장소 밖에서만 취급한다.
- 모델 산출물에는 모델·스키마·생성기 버전, 순서가 보존된 특성 목록, 특성 시점, 난수 시드, 학습 구성, 데이터 체크섬과 의존성 버전을 함께 기록한다.
- 모델 파일이 없거나 계약이 맞지 않으면 ML 결과를 `unavailable`로 반환하고 규칙 결과를 예측 확률로 대체하지 않는다.

## 9. 변경 관리

- 데이터 계약 변경은 `data-spec.md`와 관련 테스트를 함께 갱신한다.
- 제품 범위나 완료 조건 변경은 `product-spec.md`에서 팀 합의를 먼저 기록한다.
- 기술 스택의 주요 변경은 이 문서에 이유, 호환성 및 폐쇄망 영향을 기록하고 승인 후 구현한다.
- 임상 규칙과 경보 임계값은 출처와 상태가 근거 레지스트리에 등록된 경우에만 기본값으로 채택한다.
